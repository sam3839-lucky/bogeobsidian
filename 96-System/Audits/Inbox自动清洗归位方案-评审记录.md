# 第一轮评审（对 V1）

评审视角：严苛导师，压力测试假设，检查与既有规则的一致性。

## 发现的问题

1. **原则与第二层冲突**：原则 1 说"不自动移动文件"，但第二层写"AI 相关文档归 89-Prompts/AI工具使用"——暗示自动归位，自相矛盾。所有归位（含 AI 文档）应统一走第三层人工放行，保持一致。
2. **踩"未确认不批量生成"红线**：构建日志明确"未经确认不批量生成原子笔记"。第二层"自动提炼候选笔记"若理解为批量落正式笔记，会违反该红线。须限定第二层只产出"待核验候选草稿"，不批量写入正式笔记。
3. **cleaned 副本位置缺失**：未指明 cleaned 副本放哪。应明确用 `00-Inbox/Cleaned`（Folder Responsibilities 已定义该目录职责），而非散落。
4. **重复处理风险**：仅含糊提"通过标记区分"，未定义"已处理"标记机制，定时任务可能重复清洗。
5. **去重判定模糊**：URL/哈希/标题三者关系、阈值、同名不同内容误判的处理未定义。
6. **失败处理缺失**：单文件清洗失败如何处置（重试/跳过/标记 error）未定义。
7. **敏感信息扫描无规则**：扫描哪些模式、命中后是否拦截入库未定义。
8. **报告保留策略缺失**：96-System/Audits 会无限膨胀，无保留/滚动策略。
9. **触发频率与空闲期**：未定频率、空桶时是否空跑。
10. **版权边界**：导入指南要求避免复制受版权保护的完整内容，清洗层需只做格式规范化、不改写，且原件不动。

## 修订方向（→ V2）

- 统一"归位一律走第三层人工放行"。
- 第二层限定为"候选草稿 + 待核验清单"，不批量写正式笔记。
- cleaned 副本明确放 `00-Inbox/Cleaned`。
- 定义"已处理"标记（frontmatter `workflow/processed` 或处理清单哈希表）。
- 明确去重：URL/标题为主、哈希兜底；同名不同内容记入待核验。
- 单文件失败：标记 `workflow/error`，保留原样，不阻塞批次。
- 敏感信息：定义模式白名单与拦截规则（命中即标 low + 人工）。
- 报告保留：滚动保留最近 N 份，或按季度归档。
- 触发频率：默认每日一次；空桶跳过。
- 版权：清洗只做格式规范化、不改写观点，原件保留。

# 第二轮评审（对 V2）

评审视角：继续压力测试，并核对"自动化"承诺是否经得起现实检验。

## 发现的问题

1. **定时自动化能力未验证即承诺**：V2 写"触发：Codex 定时自动化（需该功能可用且线程存活）"，但仍把"每日定时"作为默认。若该自动化在用户环境中不可用、线程休眠或被沙箱拦截，任务会**静默失败**，用户无法察觉。→ 必须先验证自动化能力可用；在未验证前降级为"手动触发 + 半自动"，并加**心跳/失败可见性**（每次运行留状态标记与最后运行时间，供用户一眼看到是否成功）。
2. **"自动批量清洗"是重复性写操作**：L1 每次运行都会写入 cleaned 副本。虽可回滚，但属周期性的文件写入动作。→ 自动运行须用户**显式确认开启**（硬门槛），默认不自动开跑。
3. **自动化 Cleaner 当前 NOT_CHECKED**：幂等测试与信息无损测试尚未通过（Build-State / Cleaner Spec 明确）。→ 即便"档 1"，批量自动清洗**当前也不可上线**；必须先小规模监督试点通过后方可放开。方案须明确"当前不上线自动批量"。
4. **LLM 提炼层来源分离可核验性不足**：V2 说建议标注 AI、事实分离，但未定义**如何核验**。→ 每条建议须引用 cleaned 内容中的来源位置（锚点/原文片段），并禁止 AI 虚构作者、日期、链接等来源元数据。
5. **附件/图片迁移与链接一致性缺机制**：放行时附件随迁并更新链接，但未定义迁移后**broken-link 校验**与附件命名规则。→ 放行流程须含"链接完整性校验"步骤。
6. **去重"已入库索引"无维护者与校验**：索引若过期/不完整，去重会漏判，重复内容混入。→ 改为**放行时登记 registry**（URL/哈希），并在每次运行前校验 registry 与现有正式库一致。
7. **与既有 Triage / Import 流程关系未澄清**：L2 自动生成候选，可能被理解为绕过 Triage 的"相关性/可处理性"人工判定。→ L3 人工放行须**并入 Triage 判定维度**（安全、来源、重复、相关性、可处理性、去向），不能只做"是/否"放行。
8. **待核验清单生命周期未定义**：approved/rejected 后条目如何从队列移除或标记，否则队列会越来越乱。→ 定义清单条目的状态流转（待核验 → 已放行/已拒绝/已归档）。
9. **不可清洗格式未处理**：PDF 扫描件 / OCR 无法信息无损的格式，机械清洗会失败。→ 标记 `workflow/error` 或 `quality/needs-verification`，保留 Downloaded，不强清洗。
10. **批处理规模未设上限**：单轮处理大量文件不利监督。→ 每轮处理设上限（小批量），分批推进，便于人工逐批把关。

## 修订方向（→ V3）

- 自动化能力未验证前：默认"手动触发 + 半自动"，不承诺定时。
- 加心跳/失败可见性（状态标记 + 最后运行时间）。
- 自动批量清洗须用户显式确认开启（硬门槛）。
- 明确"当前不上线自动批量"：先监督试点通过幂等/信息无损测试。
- LLM 建议须带来源锚点，禁止虚构来源元数据。
- 放行流程含链接完整性校验。
- 去重改用"放行时登记 registry + 运行前校验"。
- L3 人工放行并入 Triage 六维判定。
- 定义待核验清单条目状态流转。
- 不可清洗格式标记 error/low 保留 Downloaded。
- 每轮批处理设上限。
