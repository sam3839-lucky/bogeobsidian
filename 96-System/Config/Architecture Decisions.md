# Architecture Decisions

## ADR-001：以 E:\波哥Obsidian 作为唯一 Vault 根目录

- 状态：已接受
- 日期：2026-08-09 12:32:50 +08:00
- 背景：阶段 0 发现 `.obsidian` 曾位于下一层目录；用户已将 Vault 内容移至 `E:\波哥Obsidian`，复核确认根目录直接包含 `.obsidian`。
- 决策：后续所有相对路径均以 `E:\波哥Obsidian` 为根，不再使用 `波哥财道` 子目录作为 Vault。
- 影响：避免在 Vault 外误建知识库结构；任何写入前仍须验证根目录存在 `.obsidian`。

## ADR-002：Git 初始化前使用 Vault 外时间戳压缩快照

- 状态：已接受
- 日期：2026-08-09 12:32:50 +08:00
- 背景：当前 Vault 不是 Git 仓库，无法使用 commit 作为回滚点。
- 决策：阶段 1 使用 `E:\波哥Obsidian-Backups\波哥Obsidian-20260809-123250.zip` 作为回滚点；备份位于 Vault 外，不覆盖旧备份。
- 影响：恢复时须先保护当前状态，再将快照解压回 Vault；Git 初始化留待后续明确阶段。

## ADR-003：系统记录与业务知识结构分离

- 状态：已接受
- 日期：2026-08-09 12:32:50 +08:00
- 背景：需要跨阶段记录执行状态，但本阶段禁止改变业务知识结构。
- 决策：仅在 `96-System` 下建立日志与架构决策文件，不创建 AI、房地产、小孩教育或内容平台目录。
- 影响：业务目录设计必须由后续阶段单独决策与执行。
## ADR-004：Git 跟踪边界与私有远端

- 状态：已接受
- 日期：2026-08-09 12:48:51 +08:00
- 背景：Vault 需要版本回滚能力，用户提供私有仓库 `https://github.com/sam3839-lucky/bogeobsidian`；设备工作区状态及凭据不应进入版本历史。
- 决策：使用 `main` 分支和 `origin` 私有远端；跟踪可复用的 Obsidian 配置与知识文件，忽略 `workspace.json`、缓存、回收站、临时文件及常见凭据文件。
- 影响：插件 `data.json` 默认不纳管，避免意外提交插件令牌，但部分插件个性化设置不会随 Git 同步。禁止 Force Push；远端已有历史时必须先审查再决定整合方式。
- 实施结果：首次 Push 已通过 Clash Verge 一次性代理完成；代理未写入 Git 全局配置；验证提交为 `6cea82b8d142031edd8e91709e252e9119b00e76`。
## ADR-005：采用按需落地的最小目录架构

- 状态：已接受
- 日期：2026-08-09 13:09:48 +08:00
- 背景：目标结构包含多个生命周期与研究目录，但当前业务内容只有根目录 `欢迎.md`。创建空目录无法进入 Git，使用大量 `.gitkeep` 会制造虚假完成感和维护噪音。
- 决策：完整定义目标目录职责，但仅在出现首个真实内容或本阶段指定文件时创建目录。本阶段只新增有实际治理文档承载的 `96-System/Guides`。
- 影响：目标结构将逐步出现，而不是一次性铺满；目录是否存在不能单独代表功能是否完成。

## ADR-006：目录表达职责与生命周期，Topic 表达关联

- 状态：已接受
- 日期：2026-08-09 13:09:48 +08:00
- 背景：AI、房地产、小孩教育可能同时参与研究、项目和内容生产；若用多套深层目录表达所有交叉关系，会导致重复文件和版本分叉。
- 决策：每份知识只有一个主存放位置；目录表示主要职责或生命周期，Topic、链接及后续元数据表示跨领域关系。目录原则上不超过三层。
- 影响：跨领域内容不得复制到多个研究目录；`07-Topics` 只在已有真实笔记需要导航时创建。
## ADR-007：采用统一基础 Properties 与类型状态兼容表

- 状态：已接受
- 日期：2026-08-09 13:24:43 +08:00
- 背景：不同笔记需要统一检索字段，但强迫每类笔记填写全部字段会制造虚假数据。
- 决策：所有新笔记共享英文基础字段；`id`、`type`、`title`、`status`、`created` 通用必填，其余按类型条件填写。`domain` 最多一个，`topics` 可多选，`tags` 只承担注册的操作性信号。
- 影响：现有笔记不批量注入 YAML；新增字段、类型、状态或标签必须先修改治理规范。

## ADR-008：核心模板使用无插件静态 YAML

- 状态：已接受
- 日期：2026-08-09 13:24:43 +08:00
- 背景：当前未安装模板自动化插件，动态占位符无法可靠解析，也可能生成虚构日期或标识。
- 决策：11 个核心模板使用 Obsidian 原生静态 YAML；必填实例值保持空字符串，并在复制后手工填写。验证采用真实审计记录，不创建 Topic Hub 或伪知识。
- 影响：创建笔记时需要手工生成 `id` 和日期；自动化只能在未来插件阶段经确认后增加，且必须保留无插件版本。
## ADR-009：Cleaner 采用原件不可变与双工件输出

- 状态：已接受
- 日期：2026-08-09 13:40:41 +08:00
- 背景：格式清理可能误删观点、来源、代码、表格或导航内容，直接覆盖原件会失去审计和回滚能力。
- 决策：Downloaded 原件不可变；Cleaner 只生成新的 cleaned 副本和独立审查清单。分类、Topic 与链接仅作为 AI 或规则建议，不写入原文事实区。
- 影响：存储会暂时保留原件与清理副本，但正式知识仍只有一个主位置；原件的后续处置必须单独批准。

## ADR-010：Triage 与 Reviewed 是人工关卡，不扩展受控 status

- 状态：已接受
- 日期：2026-08-09 13:40:41 +08:00
- 背景：阶段 4 流程包含 Triage 和 Reviewed，但阶段 3 已定义受控 `status`，直接加入新值会破坏元数据治理。
- 决策：Triage 和 Reviewed 作为流程关卡记录在审查清单中，不创建同名目录，也不新增 `status` 值。自动化只生成建议，正式流转由人工确认。
- 影响：当前可进行单文件人工监督试运行；自动化 Cleaner 未实现前禁止批量运行。
## ADR-011：Topic Hub 必须由真实语义关系和维护需求驱动

- 状态：已接受
- 日期：2026-08-09 13:49:21 +08:00
- 背景：当前 `04-Research` 不存在，真实研究文件为 0。若直接以声明领域、模板或词频创建 Hub，会产生空 Topic 和伪知识图谱。
- 决策：Hub 默认至少需要 3 份真实相关文件，或 2 份真实文件加明确项目/创作需求；还必须通过长期价值、语义关系、当前重点、需求和可维护性评估。没有获批 Hub 时不创建 Topic Index。
- 影响：本阶段只创建 Topic Governance 和准入评估报告；不创建 `07-Topics`、Topic Index 或 Hub。

## ADR-012：阶段 5 在无真实 Research 时进入规则完成、试点阻塞状态

- 状态：已接受
- 日期：2026-08-09 13:49:21 +08:00
- 背景：阶段 4 允许单文件人工试运行，但尚未导入任何真实资料。
- 决策：规则与审计可以落地，实际分类、YAML、标签、链接、Topic 和 Hub 修改全部停止，直到真实资料满足准入并获得确认。
- 影响：阶段编号不等于业务试点已完成；Build State 必须分别记录治理规则与试点状态。

## ADR-013：旧 Research 元数据采用保守归一化

- 状态：已接受
- 日期：2026-08-10 14:23:36 +08:00
- 背景：阶段 5 只读审计发现 3 份旧 Research 缺少稳定 ID、主领域、来源和可信度，且存在未注册状态和标签。
- 决策：只规范化 YAML；正文不可变；非法 `collecting` 映射为 `draft`；保留既有 period、location、scope、source_scope 等上下文字段；不修改最后一份 domain 为空的消费政策资料。
- 影响：元数据可参与 Topic 分析，但旧文档仍可能需要逐篇人工来源核验；任何 Hub 创建前必须基于修复后的字段重新评分。

## ADR-014：项目与内容生命周期使用独立受控状态

- 状态：已接受
- 日期：2026-08-10（Asia/Shanghai）
- 背景：阶段 6 要求项目状态和内容生产流可验证；原有 `project` 与 `content-brief` 状态不足以表达 planned、blocked、review 和 repurpose 等关卡。
- 决策：项目使用 `planned`、`active`、`blocked`、`paused`、`completed`、`archived`；内容使用 `idea`、`brief`、`draft`、`review`、`published`、`repurpose`、`archived`。`Scripts` 是内容形式与目录职责，不作为状态。Review 与 Repurpose 先作为状态关卡，不为零内容机械创建空目录。
- 影响：阶段 6 之后的新项目与 Content Brief 必须使用新状态；当前不存在相关真实实例，因此无需迁移旧文件。

## ADR-015：“房产视频文案”建模为内容形式而非主领域

- 状态：已接受
- 日期：2026-08-10（Asia/Shanghai）
- 背景：“房产视频文案”同时包含房地产主题和视频文案形式；把它与 AI、房地产、小孩教育并列会造成主领域重复和检索歧义。
- 决策：继续保持受控 `domain` 为 `AI`、`房地产`、`小孩教育`。房产视频文案使用 `domain: "房地产"`，在 Content Brief 正文记录内容形式，并可在有真实语义关系时使用 topic；`format/video` 仅在满足标签治理规则时使用。
- 影响：不创建 `04-Research/房产视频文案` 或平台专属目录；未来若用户明确内容平台，应先更新治理规范再决定目录或字段。

## ADR-016：导航索引不伪装成业务实体

- 状态：已接受
- 日期：2026-08-10（Asia/Shanghai）
- 背景：Prompt Index、项目 `Decisions.md` 和 `Resources.md` 只负责导航。如果强行标记为 `prompt`、`decision` 或 `source`，会产生无法满足类型语义的伪记录。
- 决策：上述导航文件可不设 YAML；真实 Prompt 各自使用 Prompt Template，具体决策使用 Decision Template，具体来源保留在唯一主位置。真实项目的项目级 YAML 只放在 `Project-Status.md`。
- 影响：索引不参与业务实体统计；验证器应只对含 frontmatter 的文件执行 YAML 与 type/status 检查。
## ADR-017：三层内容模型与房地产深圳细分

- 状态：已接受
- 日期：2026-08-13（Asia/Shanghai）
- 背景：用户需要把收集内容长期沉淀为可产出视频号/公众号文案的知识库。确认的模型分三层：① 内容主题域（仓库）＝房地产（主、深圳细化）＋小孩教育；② 生产层（加工厂）＝知识→选题清单→文案；③ 能力层（磨刀石）＝AI 使用经验，纯内部。AI 不是内容主题，而是服务房地产/教育内容的生产工具与方法层。
- 决策：
  - 受控 domain 保持 AI、房地产、小孩教育，但 AI 不再作为内容主题域使用；AI 相关内容一律进能力层（89-Prompts、97-AI-Memory、98-AI-Context、96-System），不进 04-Research/AI 作为主题仓库。
  - 04-Research/房地产 内按内容用途细分：政策、板块分析、选房策略、为什么买房、市场行情、热点事件/土拍、热点事件/成交、其他城市、原始资料。
  - 深圳按上述子类细化；其他城市一律进 其他城市 单文件夹，不细分。
  - 为什么买房 作为常识性、可长期复用的常驻题材，独立成目录持续积累。
  - 07-Topics 只负责跨笔记导航，不承担物理细分职责。
- 影响：04-Research/AI 不再作为内容主题位使用；是否物理删除由后续内容出现情况决定。目录只跟随真实内容创建，空目录一律不建（沿用 ADR-005）。

## ADR-018：财商提升为与房地产同级的顶级主题域

- 状态：已接受
- 日期：2026-08-13（Asia/Shanghai）
- 背景：`04-Research/房地产/财商` 已积累真实财商知识笔记（《钱生钱的速度永远比劳动生钱更快》）。用户确认：财商不再是房地产的子类，而应与 房地产、小孩教育 同为 `04-Research` 下的顶级主题域。
- 决策：
  - 受控 domain 增加 `财商`，与 `房地产`、`小孩教育` 并列；财商内容主领域归 财商。
  - `04-Research/财商` 为独立顶级目录，与 `04-Research/房地产`、`04-Research/小孩教育` 平级。
  - 原规则点 6 修订：财商等跨领域内容不再并入 房地产；涉及具体房贷/房产资产配置的内容通过 topics 关联 房地产。
  - 既有财商笔记的 domain 由 房地产 迁移为 财商（逐份经用户确认后执行）。
- 影响：本决策推翻 ADR-017 中以「房地产＋小孩教育」列举的顶级主题域范围，以及原规则点 6「财商主领域归房地产」；不改变三层内容模型结构，财商在 ① 层与 房地产 同级。受控 domain 新增须同步 Metadata Schema 与 Folder Responsibilities。

## ADR-019：内容生产采用任务编排、资产正文与哈希审核的分层真相

- 状态：已接受
- 日期：2026-08-14（Asia/Shanghai）
- 背景：`05-Content` 已存在 `content-brief`、`viral-design` 和 `script`，但正式 Metadata Schema 尚未登记后两者，也没有聚合一条选题全流程的任务实体。部分旧 Brief 使用 `brief` 状态，部分爆款设计缺少 status；若插件根据文件名、文件存在或历史模糊状态推断审核与发布，会制造不可追溯的假状态。
- 决策：
  - 新增受控类型 `content-task`、`viral-design`、`script`；继续使用 `content-brief`。`topic-candidates` 与旧 `brief` 类型只读兼容，不作为新的正式写入类型。
  - `content-task.status` 使用 `active`、`blocked`、`completed`、`archived`；`current_stage` 独立使用 `inbox`、`idea`、`brief`、`viral_design`、`drafting`、`human_review`、`publishing`、`retrospective`、`archived`。
  - `content-brief` 与 `viral-design` 的 canonical status 使用 `draft`、`review`、`approved`、`archived`；`script` 使用 `draft`、`review`、`ready`、`published`、`skipped`、`archived`。双平台分别使用 `not_started`、`draft`、`review`、`ready`、`published`、`skipped`，不得以一端状态推断另一端。
  - 任务文件保存 `schema_version`、`revision`、`current_stage`、`source_ids`、资产 ID、平台状态与审核记录。稳定 ID 是正式关联；路径和 Obsidian 内部链接是可重建导航，不是关联真相。
  - 任务文件负责流程阶段、revision 和平台编排；资产文件负责正文及自身 status；审核记录只对指定 `asset_id` 的精确原始字节 SHA-256 有效。资产发生任何字节变化后，旧审核立即失效。
  - 审核时先写入并回读资产的最终 canonical 状态，再计算最终字节哈希，最后把审核记录写入任务；禁止对即将继续修改的旧字节先行签名。
  - 旧 `content-brief.status: brief` 只能读取为待确认历史状态，不能自动视为 approved；旧中文 platform 值可兼容读取，新写入统一使用 `video_channel` 和 `wechat_article`；当前任务关联资产出现缺 status、未知 type/status 或重复 ID 时 fail closed，无关旧文件只进入体检报告。
  - 首次运行只报告不合规项。批量迁移禁止；只有用户确认过逐字段 diff 的试点任务可以写入，且必须幂等。
  - 多文件写入必须经过持久化恢复协议；MVP 禁止删除正式文件，以 archived/skipped 表达退出。
- 影响：编码前必须把本决策同步到 `Metadata Schema.md` 并用 fixtures 验证兼容读取；插件不得从文件名或文件存在性推断阶段、审核或发布。现有文件不因本 ADR 自动修改。
