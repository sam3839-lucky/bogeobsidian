# 内容生产驾驶舱工程测试计划

## 一、目的

本计划不是测试页面“能不能点”，而是证明插件不会丢文件、覆盖外部修改、伪造审核通过或错误合并双平台状态。

## 二、测试环境

| 环境 | 用途 | 数据 |
|---|---|---|
| Node + Vitest | 纯函数和仓储集成测试 | 内存 fixture / 临时目录 |
| 独立测试 Vault | Obsidian API、插件安装和恢复 | 3 条试点的脱敏副本 |
| 主 Vault 副本 | 规模、主题和兼容回归 | 294 份 Markdown 的只读/可回滚副本 |
| 主 Vault | 最终人工试点 | 仅安装已通过构建；先快照 |

禁止在主 Vault 里注入崩溃、磁盘满、损坏 manifest 和并发写入场景。

### 3.4 操作日志与崩溃恢复

| ID | 注入点/场景 | 预期 |
|---|---|---|
| REC-01 | old/new 快照写入前失败 | 正式文件零变化 |
| REC-02 | 快照写一半或磁盘满 | 正式文件零变化，无有效 prepared |
| REC-03 | temp manifest 完成、rename 前崩溃 | temp 不参与恢复 |
| REC-04 | manifest 发布、pending 前崩溃 | 发现 orphan；全旧时可放弃/继续 |
| REC-05 | pending 后、首资产前崩溃 | 可继续或完整回滚 |
| REC-06 | 第一资产后崩溃 | old 继续、new 跳过，最终幂等 |
| REC-07 | 多资产中途外部修改为第三 hash | conflict，禁止自动覆盖/回滚 |
| REC-08 | 所有资产完成、任务提交前崩溃 | revision 未变则重试任务提交 |
| REC-09 | 任务 revision 已变化 | manual_repair |
| REC-10 | 任务提交后、committed manifest 前崩溃 | 全新 hash 时补记 committed |
| REC-11 | 回滚中途崩溃 | 逆序幂等继续 |
| REC-12 | 回滚目标被外部修改 | 停止回滚，manual_repair |
| REC-13 | manifest 最新版损坏、旧版有效 | 选最高有效旧版 |
| REC-14 | 所有 manifest 损坏 | 不自动处理 |
| REC-15 | old/new snapshot hash 不符 | 不自动处理 |
| REC-16 | create 目标被用户抢先创建 | conflict，不覆盖 |
| REC-17 | 同一任务启动第二操作 | mutex/pending 拒绝 |
| REC-18 | committed 7 天清理 | 只删终态恢复工件 |
| REC-19 | conflict 超过 7 天 | 永不自动清理 |
| REC-20 | 插件反复重启同一恢复任务 | 结果稳定，无重复写 |

## 四、覆盖率与合并门槛

- `src/domain/**`：100% branch coverage。
- `src/vault/recovery/**`：100% branch coverage。
- 其他纯逻辑模块：≥90% branch coverage。
- UI 不用无意义行覆盖率替代 E2E；14 个核心页面/状态至少各有一条行为测试或验收脚本。
- TypeScript、ESLint、Vitest、build、release artifact verify 必须全绿。
- P0/P1 为 0 才能进入主 Vault 试点。

## 五、P0 判定

以下任一项出现即停止试点：

- 数据丢失或覆盖第三版本。
- AI 或规则自动宣布人工审核通过。
- 双平台状态错误合并。
- 恢复日志损坏后仍自动继续/回滚。
- duplicate ID 下仍写入。
- 密钥写入 Vault、data.json、日志或 Git。
- 主 Vault 被测试脚本自动修改。

## 六、每个切片的验收证据

每个切片必须保存：

1. 测试命令与退出码。
2. 覆盖率摘要。
3. 关键 E2E 截图或录屏。
4. 测试 Vault 前后文件 hash 清单。
5. 已知限制与未执行测试。
6. 回退步骤。

不得以“代码已写完”代替“已验证完成”。
