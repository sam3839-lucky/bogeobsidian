# 内容生产驾驶舱工程架构评审

## 一、评审结论

**结论：APPROVED，可以进入工程脚手架阶段，但不能跳过纵向切片顺序。**

本轮锁定五项工程决策：

1. 元数据采用 `content-task + 资产文件 + 哈希审核记录` 的分层真相模型，正式记录为 `ADR-019`。
2. 插件源码放在 `E:/obsidian-kb-v2-dev/plugins/content-production-dashboard/`，不放进 Vault，也不放进 `.obsidian/plugins/` 开发。
3. 三条试点按稳定 ID 映射；试点映射不等于内容已核验，也不自动导入历史审核结论。
4. 多文件写入采用不可变操作日志、原始字节 SHA-256、比较后写入和确定性恢复；MVP 禁止删除文件。
5. 测试采用纯函数单元测试、测试 Vault 集成测试和 Obsidian 桌面端关键链 E2E 三层矩阵；恢复协议属于合并阻断项。

这不是“把原型全部一次性写完”的批准。第一版必须按 6 个纵向切片逐步交付，每个切片均需可独立验证和回退。

```text
+------------------+-------------------+----------------------+
                   |                   |
+------------------v------+   +--------v---------------------+
| Vault Adapter           |   | AI Adapter                   |
| ID Multi-Index/Repo/CAS |   | requestUrl / Preview / Retry |
| Journal / Recovery      |   | SecretStorage                |
+------------------+------+   +--------+---------------------+
                   |                   |
+------------------v-------------------v---------------------+
| Markdown/YAML 唯一业务事实 + 插件私有恢复日志              |

```

### 3.1 真相边界

- Vault 中 Markdown/YAML 是唯一业务事实。
- 内存 ID 索引可随时从 Vault 重建，不是事实来源。
- 恢复日志只证明一次写操作的旧值、新值和进度，不是内容资产。
- AI 输出在人工接受前只是预览，不得写成正式资产。
- Python/数据库数据不得反向覆盖 Vault。

### 3.2 运行边界

- MVP `isDesktopOnly: true`。
- `onload()` 只注册视图、命令、设置和事件，不扫描全库。
- 初始索引在 `workspace.onLayoutReady()` 后构建。
- 后续通过 create/modify/delete/rename 事件增量维护索引。
- UI 渲染禁止触发全 Vault 扫描。

### 3.3 官方技术依据

- [Obsidian Plugin guidelines](https://docs.obsidian.md/oo/plugin)：使用 `Vault.configDir`，避免硬编码 `.obsidian`；网络请求使用 `requestUrl`；文件元数据优先使用 Vault/FileManager API；设置使用 `loadData/saveData`。
- [Obsidian Vault API guide](https://docs.obsidian.md/Plugins/Vault)：需要比较后修改时使用 `Vault.process()`，保证回调读取与写入之间没有其他文件变化。
- [Obsidian secret storage](https://docs.obsidian.md/plugins/guides/secret-storage)：设置只保存 secret 名称，密钥值进入 `SecretStorage`，不得写入 `data.json`。
- [Obsidian load-time guide](https://docs.obsidian.md/plugins/guides/load-time)：`onload()` 保持轻量，布局相关初始化推迟到 `onLayoutReady()`。
- [Obsidian sample plugin](https://github.com/obsidianmd/obsidian-sample-plugin)：采用独立 TypeScript/esbuild 包和锁文件，发布工件为 `main.js`、`manifest.json` 及可选 `styles.css`。

## 四、元数据 ADR 锁定

正式决策见 `96-System/Config/Architecture Decisions.md` 的 `ADR-019`。本节是工程解释，不再形成第二份规范。

### 4.1 三层真相

```text
content-task
  |- current_stage / revision / platform states / asset IDs
  |
  +--> content-brief       正文与资产 status
  +--> viral-design       正文与资产 status
  +--> script(video)      正文与资产 status
  +--> script(article)    正文与资产 status

approval(asset_id, sha256)
  只证明“人工批准过这一份精确字节”
```

### 4.2 受控类型与状态

| type | canonical status |
|---|---|
| `content-task` | `active`, `blocked`, `completed`, `archived` |
| `content-brief` | `draft`, `review`, `approved`, `archived` |
| `viral-design` | `draft`, `review`, `approved`, `archived` |
| `script` | `draft`, `review`, `ready`, `published`, `skipped`, `archived` |

任务阶段：

`inbox → idea → brief → viral_design → drafting → human_review → publishing → retrospective → archived`

双平台状态分别保存，取值为：

`not_started | draft | review | ready | published | skipped`

`status` 回答“任务是否活跃/阻塞/完成”，`current_stage` 回答“任务进行到哪一步”。二者禁止混用。

### 4.3 关联规则

- 稳定 ID 是正式关联；路径和内部链接只用于导航。
- 任务卡保存 `source_ids` 与各资产 `asset_id`，不复制正文。
- 文件重命名或移动后，ID 关联仍有效；插件可重建导航链接。
- 当前任务关联资产出现 duplicate ID、缺失 ID、未知 type/status 时阻塞该任务写入；无关旧文件只进入体检报告，不能瘫痪整个插件。

### 4.4 兼容规则

- 旧 `content-brief.status: brief` 只读为“待确认的历史状态”，不能自动视为 `approved`。
- 旧 `platform: 视频号/公众号` 可读取，正式写入统一为 `video_channel/wechat_article`。
- 缺少 `status` 的 `viral-design` 是不合规资产，首次体检只报告；试点迁移预览必须让用户确认拟补值。
- 旧 `type: brief` 和 `topic-candidates` 只提供只读兼容，不作为新的正式写入类型。
- 首次运行不批量改旧文件，不根据文件名猜测类型，不导入不存在的审核结论。
- 现有产品和 UX 方案使用尚未注册的 `type: plan`，属于系统文档元数据债务；插件不得把它误当内容资产。是否注册系统计划类型应另行治理，不夹带进本次内容资产 ADR。

### 4.5 审核哈希顺序

批准一份资产时必须按以下顺序：

1. 先把资产写成最终 canonical 状态并重新读取。
2. 对最终原始 UTF-8 字节计算 SHA-256。
3. 再把 `asset_id + sha256 + approved_at` 写入任务。
4. 以后只要当前哈希不同，审核立即失效。

如果先计算哈希再修改 `status`，批准记录会在创建当刻失效，因此禁止该顺序。

### 4.6 元数据债务与修复后基线

工程评审时发现以下既存债务，均不是评审新增：

- 4 组重复 ID，集中在原始件、清洗件或归档件的成对副本。
- 7 份 `viral-design` 缺少 `status`，其中包括试点 A、B。
- 产品与 UX 方案使用未注册的 `type: plan`；它们不是内容资产。

2026-08-14 已完成定向修复：原始件保留导入 ID，3 份正式 cleaned 与 1 份归档 cleaned 获得新 ID；7 份完整但无历史哈希审核记录的爆款设计补为 `review`。修复后全库重复 ID 为 0，`viral-design` 缺 status 为 0。`type: plan` 仍作为独立系统文档治理问题保留，不夹带处理。

即使当前重复 ID 为 0，ID 索引仍必须实现为 `Map<id, Set<path>>`，而不是会静默覆盖的 `Map<id, path>`；未来一旦任务来源或资产指向重复 ID，该任务立即阻塞。

## 七、文件恢复协议锁定

### 7.1 恢复目录

```text
<vault.configDir>/plugins/content-production-dashboard/recovery/<operation_id>/
|- manifest-0001.json
|- manifest-0002.json
|- old/<target-key>.bin
`- new/<target-key>.bin
```

恢复目录不进入业务目录、内容索引和 Git。路径必须使用 `Vault.configDir`，禁止硬编码 `.obsidian`。

恢复日志要求 temp + flush/fsync + atomic rename，创建正式文件还要求排他式 `create-if-absent`。普通 Vault API 没有同时覆盖这两个底层保证，因此 MVP 仅在确认 `vault.adapter` 是 `FileSystemAdapter` 后，使用 Node 文件 API处理插件私有日志和正式文件的排他新建；现有业务文件修改仍使用 `Vault.process()`。这是一项范围很窄、必须测试的例外，也是 `isDesktopOnly: true` 的直接原因。若运行环境不是 FileSystemAdapter，插件只读体检并禁止写入，不得退化成较弱协议。

### 7.2 操作状态机

```text
preparing -> prepared -> applying -> committed
                 |            |
                 |            +-> conflict -> manual_repair
                 |
                 +-> rollback_in_progress -> rolled_back
```

每个目标文件还有独立状态：`prepared → applied → rolled_back`。

### 7.3 写入协议

1. 获取任务内存互斥锁，读取任务 `revision` 和所有目标文件原始字节。
2. 纯函数生成全部目标新字节，旧/新均计算 SHA-256；对现有文本文件，以 `Vault.process()` 回调所提供字符串的 UTF-8 字节作为 CAS 哈希输入，哈希前不做 BOM 或换行规范化；新建目标的旧哈希使用 `ABSENT`。BOM/CRLF 的实际 API 往返行为必须由 `META-07` 在目标 Obsidian 版本锁定。
3. 写入 old/new 快照并回读验证。
4. 以临时文件、刷新、原子 rename 发布不可变 `manifest-0001.json`。
5. 操作日志存在后，才用 CAS 在任务登记 `pending_operation`。
6. 资产优先、任务最后。每次写前使用 `Vault.process()` 比较当前原始字节哈希和预期旧哈希，再返回准备好的精确新文本。
7. 每完成一项，追加下一版不可变 manifest；不覆盖旧 manifest。
8. 所有资产成功后，以任务旧 revision 为前提提交任务、清除 `pending_operation`、revision 加一。
9. 回读正式文件，核对新哈希后再标记 `committed`。

普通单文件 frontmatter 编辑优先使用 `FileManager.processFrontMatter()`；需要跨文件确定性恢复时，为得到可预计算的新字节，允许在仓储层使用受控的完整文本 codec + `Vault.process()`。这是安全例外，必须有字节级往返测试。

### 7.4 崩溃点与恢复裁决

| 崩溃点 | 启动后裁决 |
|---|---|
| manifest 发布前 | 没有正式操作；清理临时文件 |
| manifest 已发布、pending 未写 | 识别孤儿准备操作；全为旧哈希时可放弃或继续 |
| pending 已写、尚无资产写入 | 可继续或安全回滚 |
| 部分资产 applied | 当前为新哈希的保留，旧哈希的继续；第三种哈希转人工 |
| 全资产 applied、任务未提交 | revision 未变时优先重试任务提交 |
| 任务已提交、manifest 未标 committed | 重读任务和资产；全为新哈希则补记 committed |
| 回滚中断 | 只对“当前等于新哈希”的目标逆序继续回滚 |

### 7.5 禁止自动处理的情况

- 当前文件既不是 old hash 也不是 new hash。
- 任务 revision 已被外部修改。
- manifest 无任何结构和校验和有效版本。
- 快照丢失或快照自身 hash 不匹配。
- 目标路径出现用户新建文件，且该操作原计划为 create。

这些情况进入 `manual_repair`，显示旧/新/当前三方差异。插件不能选择“看起来最像”的版本。

### 7.6 清理规则

- committed/rolled_back 的操作保留 7 天后可清理。
- conflict/manual_repair/非终态永不自动清理。
- MVP 不做 delete；归档和跳过通过元数据表达。

## 八、代码质量评审

### 8.1 允许的类

只有 Obsidian 生命周期需要类：Plugin、ItemView、Modal、SettingTab。状态机、关卡、hash 判定、迁移和恢复决策使用可序列化数据结构与纯函数，避免为每种资产创建类层级。

### 8.2 必须集中处理

- frontmatter 解析和 canonical 序列化只能有一套 codec。
- ID 索引只能有一个服务。
- 文件写入只能经过 operation coordinator。
- 状态推进只能经过 gate evaluator。
- AI 错误统一分类为 auth、quota、timeout、network、cancelled、invalid-output。

### 8.3 禁止模式

- 依据文件名猜 `type/status/platform`。
- 在 UI 组件里直接改 YAML。
- 捕获异常后仍把任务显示为成功。
- 把 AI 文本直接覆盖正式文件而没有预览。
- 用 `Adapter` 遍历业务 Vault；业务文件优先使用 Vault/FileManager API。
- 在 `onload()` 做全库扫描或网络请求。
- 在日志中记录密钥、完整 prompt、用户全文或恢复快照正文。

## 十、性能评审

### 10.1 预算

以上必须在测试 Vault 和主 Vault 副本实测，不把 AI 网络等待混入本地性能指标。

### 10.2 结构性保障

- 索引构建一次，事件增量更新。
- 视图查询使用内存索引，不重复读全部文件。
- 文件变更 debounce，但人工保存产生的最后一次事件不能丢。
- journal 只包含 metadata 和快照路径，不把大正文重复塞进每个 manifest 版本。
- AI 请求支持取消；离开页面不会把迟到响应写入正式文件。

## 十一、主要失败模式

| 失败模式 | 用户可见行为 | 系统行为 |
|---|---|---|
| duplicate ID | 体检红色阻塞 | 禁止建任务和写入 |
| 资产外部修改 | 审核失效/冲突 | 比较哈希，停止推进 |
| 磁盘空间不足 | 准备失败 | 正式文件保持不变 |
| 中途崩溃 | 顶部恢复入口 | 按 manifest 恢复 |
| manifest 损坏 | 人工修复 | 不猜测进度 |
| AI 超时/额度/密钥错误 | 明确错误类别 | 预览保留，正式文件不变 |
| AI 返回非法结构 | 显示原始预览与校验错误 | 不接受，不推进状态 |
| 文件重命名 | 链接可重建 | 通过 ID 继续关联 |
| 试点内容证据不足 | 质量关卡阻塞 | 允许补来源，不允许 ready |
| 双平台只发布一端 | 仍停在 publishing | 另一端必须 published 或 skipped |
| 插件卸载/缓存删除 | 可重建 | 从 Vault 扫描恢复任务视图 |
