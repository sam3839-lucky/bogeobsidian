# 知识库驱动内容生产驾驶舱——产品设计方案

> 本方案由 `office-hours` 产品推演形成。本轮只定义产品、交互、数据边界和验收标准，不开始开发。

## 一、决策摘要

| 决策 | 结论 |
|---|---|
| 第一阶段用户 | 只服务波哥本人，不做团队协作或对外销售 |
| 产品载体 | 桌面端定制 Obsidian 插件 |
| 产品中心 | 个人内容生产驾驶舱，而非聊天机器人或通用知识库 |
| 日常入口 | 所有日常操作均在插件内完成；Codex 只负责开发维护和高级干预 |
| 技术路径 | 模块化、本地优先插件 |
| 数据真相 | Obsidian Vault 中的 Markdown/YAML 是唯一事实来源 |
| 首页逻辑 | “今日最该处理”优先，完整看板是二级页面 |
| 自动决策 | 有明确推荐时自动采用；不可逆、付费、外部发布和无明显优劣时必须人工确认 |
| 双平台发布 | 视频号与公众号分别记录审核、发布状态、日期和链接；不得合并成一个 `published` |
| 评审状态 | 产品方向已完成三轮冷启动评审：29/50 → 39/50 → 42/50；MVP UX/UI 原型已于 2026-08-14 通过用户验收；可以进入工程架构评审，不能直接编码 |

## 二、问题定义

现有知识库已经实际跑过以下流程：

`素材 → 选题 → Brief → 爆款设计 → 视频号口播稿 + 公众号文章 → 人工核验 → 发布 → 复盘 → 知识反哺`

问题不在于“没有流程”，而在于流程存在于文件和 Guide 中：

1. 用户无法一眼知道每条内容处于哪个阶段。
2. 下一步动作和退出条件依赖记忆。
3. 一个选题对应的 Brief、爆款设计和双平台稿件分散在多个目录。
4. AI 生成、人工审核、文件归档和知识提取之间缺少统一操作入口。
5. 已发布内容的数据没有形成稳定的复盘闭环。

因此，第一阶段要解决的不是“再做一个 AI 写作工具”，而是：

> 打开 Obsidian 后，插件能告诉波哥今天最该处理什么，并安全地把一条内容从素材推进到复盘。

## 三、产品目标与非目标

### 3.1 产品目标

1. 用户进入插件后 10 秒内知道今天的首要任务。
2. 用户在一个任务卡内看到来源、Brief、爆款设计、双平台稿、核验和复盘资产。
3. 插件严格执行关卡规则；AI 不能自行宣布人工审核通过。
4. 所有正式产出保存为 Markdown/YAML，退出插件后仍可在 Obsidian 中正常查看和编辑。
5. AI 生成失败、插件卸载或索引丢失时，不破坏已有知识库文件。
6. 视频号和公众号可在不同时间审核、发布或明确跳过，任务状态不会制造“双平台都已完成”的假象。

### 3.2 第一版明确不做

- 多用户、账户、角色和权限。
- 独立桌面客户端和独立业务数据库。
- Obsidian 关闭后的后台常驻处理。
- 多模型市场、工作流搭建器和插件生态。
- 视频号/公众号自动发布及自动抓取后台数据。
- 自动替用户通过审核、登记发布或填写不存在的数据。
- 复杂竞品库、复杂统计仪表盘和移动端完整生产。

## 四、设计前提

### 4.1 Vault 是唯一事实来源

- 所有正式内容、状态和关联关系写入 Markdown/YAML。
- 插件允许建立可重建的本地索引缓存，但缓存不能成为唯一数据源。
- 删除缓存或重装插件后，应能从 Vault 重建任务视图。

### 4.2 插件是唯一日常操作入口

- 用户不需要进入代码编辑器，也不需要在 Codex 对话与 Obsidian 之间来回复制。
- AI 操作表现为明确的动作按钮，例如“生成 Brief”“生成爆款设计”“根据意见修改双平台稿”。
- 第一版不采用聊天窗口作为主界面；必要的修改意见使用短输入框或批注区。

### 4.3 一条选题对应一张内容任务卡

任务卡是流程聚合对象，不复制正文。它只保存：

- 稳定 `task_id`
- 任务标题、领域、主题和优先级
- 当前阶段和进入阶段时间
- 关联来源素材
- 关联 Brief
- 关联爆款设计
- 关联视频号口播稿
- 关联公众号文章
- 关联核验记录和复盘记录
- 视频号与公众号各自的制作、审核和发布状态
- 审核时对应的文件内容哈希、审核时间和检查清单版本

现有文件继续保留在原目录；任务卡通过稳定 ID 和内部链接聚合它们。

### 4.4 人工审核是硬门槛

AI 可以生成、修改、查错和提出建议，但以下动作必须由用户明确确认：

- 选题进入正式生产
- Brief 审核通过
- 爆款设计审核通过
- 双平台稿验收通过
- 内容已实际发布
- 表现数据已确认

## 五、方案比较

### 5.1 单体插件

最快，但界面、状态机、文件读写和 AI 调用容易耦合。随着流程增加，修改一个环节可能影响全部功能。

### 5.2 模块化、本地优先插件（采用）

插件内部划分为五层：

```text
界面层
  ↓
内容任务与状态机
  ↓
关卡规则引擎
  ↓
Markdown / YAML 数据适配层
  ↓
AI 适配层
```

采用原因：既保持个人插件的部署简单，又能让工作流规则、文件结构和 AI 服务独立演进。

### 5.3 插件 + 本地后台服务

适合 Obsidian 关闭后仍需定时处理的场景。目前没有证据证明这是刚需，第一阶段不采用。后续只有在真实使用中反复出现后台任务需求时再评估。

## 六、信息架构

### 6.1 一级导航

第一版只保留四个核心入口：

1. **今日工作台**：默认首页，显示最该处理的任务。
2. **内容流水线**：查看所有任务的阶段分布与阻塞。
3. **素材 Inbox**：查看新素材，启动快速选题或归档处理。
4. **发布与复盘**：记录发布事实、录入表现数据、生成复盘。

“选题池”和“知识库搜索”作为工作台中的筛选或动作，不在 MVP 首屏独立占据一级导航；“规则与设置”放在插件设置页。

### 6.2 首页信息层级

![内容生产驾驶舱首页线框](../attachments/2026-08-14%20内容生产驾驶舱-首页线框.png)

首页按以下顺序回答问题：

1. 今天最该处理什么？
2. 为什么它排在最前？
3. 下一步只有哪一件事？
4. 这张任务卡已经有哪些资产？
5. 需要人工操作，还是可以调用 AI？

### 6.3 首页模块

- 本周目标：计划数、已完成数。
- 等待审核：只统计需要用户决策的任务。
- 流程阻塞：关卡缺项、来源失效或文件缺失。
- 待复盘：已发布且到达复盘时间的任务。
- 今日任务列表：按时效、阻塞和人工依赖排序。
- 当前任务卡：展示下一步、资产关联和可执行动作。
- 生产线概览：只显示阶段数量，点击后进入完整流水线。

## 七、核心操作流程

### 7.1 常规生产

```text
从知识库选素材
  → AI 生成选题候选
  → 用户确认选题
  → AI 生成 Brief
  → 用户审核 Brief
  → AI 生成爆款设计
  → 用户选择 Hook/标题并放行
  → AI 生成视频号稿和公众号稿
  → 用户提出修改意见或直接编辑
  → AI 辅助事实/版权/合规检查
  → 用户逐项验收
  → 用户在平台发布
  → 用户登记真实发布信息
  → 插件提醒归档和轻量提取
  → 到期录入数据并复盘
```

### 7.2 快速选题

```text
打开素材 Inbox
  → 选择一份或多份新素材
  → 点击“开始快速选题”
  → AI 提供 3–5 个角度及证据锚点
  → 用户确认一个角度
  → 创建任务卡并进入 Brief
```

若 Inbox 没有新素材，插件只提示“请先放入素材”，不得擅自改用旧素材。

### 7.3 修改与返工

用户可在稿件中直接编辑，也可输入修改意见调用 AI。AI 生成的新版本先进入预览区：

- 显示变更摘要。
- 支持逐段接受或全部接受。
- 保存前保留原文件或生成可回滚版本。
- 拒绝修改时不改变任务状态。

### 7.4 发布与复盘

- 插件不能依据文件存在推断“已经发布”。
- 视频号和公众号分别登记真实日期与链接；任一平台未发布时，任务保持 `publishing`。
- 某个平台不发布时，必须由用户明确选择 `skipped` 并填写原因，不能由 AI 推断。
- 数据缺失时显示“未采集”，不能填写零值代替。
- 复盘必须区分观察、推断、下一轮实验。

## 八、任务状态与关卡

### 8.1 任务阶段

建议任务级阶段：

```text
inbox → idea → brief → viral_design → drafting → human_review
      → publishing → retrospective → archived
```

`publishing` 是一个持续阶段：可能只有视频号已发布，也可能只有公众号已发布。任务只有在两个平台分别为 `published`，或由用户将其中一个明确标记为 `skipped` 后，才可进入 `retrospective`。

注意：这是任务卡的流程阶段，不替代每个资产文件自己的 `type` 与 `status`。

### 8.2 状态真相与审核证据

状态采用分层真相，不允许插件凭文件名猜测：

1. **任务文件**是流程编排真相：保存 `current_stage`、任务修订号和双平台状态。
2. **资产文件**是内容真相：Brief、爆款设计和稿件正文及其自身 `status` 以各自文件为准。
3. **审核记录**是放行真相：每次人工通过必须记录 `asset_id`、内容 SHA-256、审核人、审核时间、检查清单版本和逐项结果。
4. 已通过的资产一旦发生实质修改，当前哈希与审核哈希不一致，审核立即显示为“已失效”，必须重新审核；插件不得静默沿用旧结论。
5. `current_stage` 与资产状态冲突时，任务显示为 `blocked/inconsistent`，禁止继续推进，并提供“按资产修复任务状态”或“撤回资产修改”的预览，不自动选择。

双平台各自使用以下受控状态：

```text
not_started → draft → review → ready → published
     └──────────────→ skipped（选题确认后、最终核验前，仅用户确认并填写原因）
           draft ───→ skipped
          review ───→ skipped
```

### 8.3 关卡规则

| 从 | 到 | 必须满足 |
|---|---|---|
| `inbox` | `idea` | 至少一个真实素材链接 |
| `idea` | `brief` | 用户确认选题，且有证据锚点 |
| `brief` | `viral_design` | Brief 必填项完整，用户审核通过 |
| `viral_design` | `drafting` | 3 个 Hook、3 个标题、情绪曲线完整，用户选择方案 |
| `drafting` | `human_review` | 视频号稿和公众号稿都已生成且可追溯 |
| `human_review` | `publishing` | 两个平台分别完成事实、版权、合规、人设和平台专项检查；审核记录绑定当前文件哈希 |
| `publishing` | `retrospective` | 两个平台分别 `published`，或其中一个由用户明确 `skipped`；每个已发布平台有真实日期与链接；表现数据已录入或明确标记未采集 |
| `retrospective` | `archived` | 复盘完成；使用过的 Inbox 素材已归档并轻量提取 |

### 8.4 自动排序原则

首页任务建议按以下顺序计算：

1. 等待用户人工审核的任务。
2. 已阻塞超过阈值的任务。
3. 热点或有时效截止的任务。
4. 已发布且到达复盘日的任务。
5. 普通常规任务。

默认排序分数采用可解释规则：等待人工审核 `+100`；硬阻塞 `+80`，每停留一天再 `+5`（最多 `+25`）；48 小时内到期热点 `+70`；复盘到期 `+40`；高优先级 `+20`、中优先级 `+10`。人工置顶永远排在自动分数之前；同分时依次按截止时间、进入阶段时间和 `task_id` 排序。用户可以修改阈值，但插件必须显示“为什么排在这里”。

## 九、数据模型与兼容策略

### 9.1 新增任务清单文件

建议在 `05-Content` 下增加一个有内容才创建的任务目录，例如：

`05-Content/Tasks/<选题>-任务.md`

任务文件只聚合状态和链接，不复制 Brief 或稿件正文。

建议字段：

```yaml
id: "content-task-20260814-example"
type: "content-task"
title: "选题标题"
current_stage: "human_review"
created: "2026-08-14"
updated: "2026-08-14"
revision: 4
domain: "房地产"
topics: ["深圳区域与板块发展"]
priority: "high"
stage_entered_at: "2026-08-14T09:30:00+08:00"
source_assets: []
brief: "[[... - Brief]]"
viral_design: "[[...-爆款设计]]"
video_script: "[[... - 视频号口播稿]]"
article_script: "[[... - 公众号文稿]]"
review: ""
retrospective: ""
video_status: "review"
video_published_at: ""
video_publish_url: ""
article_status: "review"
article_published_at: ""
article_publish_url: ""
pending_operation: ""
```

审核记录使用结构化列表保存，并绑定资产版本，例如：

```yaml
approvals:
  - approval_id: "approval-20260814-video-001"
    asset_id: "script-20260813-shenzhen-q2-land-video"
    asset_sha256: "..."
    reviewer: "波哥"
    reviewed_at: "2026-08-14T10:20:00+08:00"
    checklist_version: "publish-review-v1"
    result: "approved"
```

### 9.2 现有元数据差异

当前 `05-Content` 已实际使用：

- `script`：22 份
- `content-brief`：17 份
- `viral-design`：11 份

但正式 `Metadata Schema.md` 尚未登记 `script`、`viral-design` 和 `content-task`，部分现有文件缺少状态字段。因此开发前必须先完成一份兼容性 ADR：

1. 登记上述类型及允许状态。
2. 明确任务阶段与资产状态的关系。
3. 插件首次运行只报告不合规项，不自动批量修改旧文件。
4. 用户确认后，才对选定的试点内容补齐关联字段。

ADR 必须在编码前明确以下冲突优先级：任务文件负责流程阶段；资产文件负责正文和资产状态；审核记录只对指定文件哈希有效。没有 ADR，工程不得开始。

### 9.3 迁移原则

- 不批量重命名现有文件。
- 不移动现有 Brief、设计稿和双平台稿件。
- 不根据相似文件名静默认定关联关系。
- 首次试点选择 3 条已有完整资产的内容，由用户确认映射。
- 迁移操作必须输出变更预览和可回滚记录。

### 9.4 文件写入与确定性恢复协议

Obsidian/Vault 不提供跨多个 Markdown 文件的数据库事务，因此插件使用“持久化操作日志 + 逐文件比较后写入”。操作日志是恢复依据，不能只在内存中保存。

#### Prepare 阶段

1. 读取任务 `revision` 和所有目标资产，生成唯一 `operation_id`。
2. 为每个目标生成确定的新内容，并计算 `old_sha256` 与 `new_sha256`。新建文件的旧状态使用明确哨兵 `ABSENT`，删除操作的新状态使用 `ABSENT`。
3. 将新内容和旧内容快照写入插件私有恢复目录，确认所有暂存物落盘且哈希正确；任何写入或磁盘空间错误都在此处终止，正式文件保持不变。
4. 写入一份操作日志，至少包含：任务旧/新 `revision`、操作类型、每个目标路径、旧/新哈希、旧/新暂存物路径、逐项状态 `prepared | applied | rolled_back`、创建/修改/删除类型、开始时间和日志自身版本。
5. 操作日志成功落盘后，才在任务文件中登记 `pending_operation: <operation_id>`；此后该任务拒绝启动第二个写操作。

操作日志不在原文件上反复覆盖，而是保存为不可变的版本快照，例如 `manifest-0001.json`、`manifest-0002.json`。每次状态变化都先在同目录写临时文件，完成写入、刷新与 JSON/校验和验证后，再原子改名为下一个序号；半写的临时文件不参与恢复。启动时选择序号最高且结构与校验和均有效的版本，旧版本保留到操作结束。若没有任何有效版本，操作不得自动继续或回滚，只能转人工修复。

#### Apply 阶段

1. 按操作日志固定顺序逐项执行。
2. 每项执行前重新读取正式文件：当前状态必须等于 `old_sha256` 或 `ABSENT`；否则判定外部冲突并停止。
3. 使用 `Vault.process()` 或 `FileManager.processFrontMatter()` 比较后写入；新建文件使用排他式“不存在才创建”，不得覆盖同路径文件。
4. 写入后立即重新读取并验证为 `new_sha256`，然后把该项状态持久化为 `applied`，再执行下一项。
5. 所有资产项 `applied` 后，最后以旧任务 `revision` 为前提提交任务链接、平台状态、审核记录与 `revision + 1`。提交成功后清除 `pending_operation`，操作日志标记 `committed`。

#### 重启恢复判定

对每个未提交操作逐项判断：

- 正式状态等于 `old_sha256` 且日志为 `prepared`：该项尚未执行，可以继续。
- 正式状态等于 `new_sha256`：该项已经执行；即使日志仍为 `prepared`，也将其校正为 `applied`，不得重复创建或重复修改。
- 正式状态既不是旧哈希也不是新哈希：发生外部冲突，只能进入人工修复，禁止自动继续或回滚。
- 回滚仅在每个已应用目标都存在已校验旧快照时开放；回滚也逐项比较当前状态必须等于 `new_sha256`，否则停止并转人工修复。
- 所有资产已应用但任务最终提交失败时，恢复流程优先重试任务提交；任务旧 `revision` 已变化则转人工修复。
- 插件启动时必须扫描 `recovery/` 下所有非终态操作，而不能只扫描任务文件的 `pending_operation`。若操作日志已落盘但崩溃发生在 `pending_operation` 登记前，将其识别为“孤儿准备操作”：正式文件全部仍为旧状态时可安全丢弃或继续；任何目标已为新状态时按正常恢复流程处理；出现第三种哈希时转人工修复。

#### 暂存物与清理

- 操作日志和暂存物保存于插件私有配置目录的 `recovery/<operation_id>/`，不进入业务目录、搜索索引和 Git。
- `committed` 或完整 `rolled_back` 后默认保留 7 天；用户可在设置中改为 1–30 天或手动立即清理。
- 未提交、冲突或恢复中的操作不得自动清理。
- 清理失败只提示磁盘占用，不影响业务文件；暂存写入、哈希校验或磁盘空间检查失败则禁止开始正式写入。

AI 输出在用户接受前只存在于预览/恢复缓冲区。恢复快照不是业务真相，不能被内容索引或任务扫描当作正式资产。

#### 哈希规范

- `old_sha256` 与 `new_sha256` 对磁盘文件的原始字节计算，不对文本做任何规范化。
- UTF-8 BOM、CRLF/LF、尾随空格、frontmatter 顺序和格式化变化都会改变哈希，均视为文件已修改。
- 插件生成新文本时固定使用 UTF-8 无 BOM 与 LF；但不得仅为统一格式批量改写旧文件。
- 内容语义比较可以另行展示给用户，但不能代替并发控制使用的原始字节哈希。

## 十、AI 设计

### 10.1 第一版 AI 动作

只实现下列明确动作，不建设通用聊天机器人：

1. 从选定素材生成选题候选。
2. 生成或补全 Brief。
3. 生成爆款设计。
4. 同时生成视频号口播稿和公众号文章。
5. 根据用户意见修改选定稿件。
6. 检查事实边界、来源、版权、广告合规和人设一致性。
7. 根据真实数据生成复盘草稿。

### 10.2 上下文最小化

每个 AI 动作只读取：

- 当前任务卡关联的素材和资产。
- 该动作需要的模板和提示词。
- 波哥人设与强制规则。

不得默认把整个 Vault 上传给模型。

### 10.3 密钥与网络边界

- 个人 MVP 使用用户自己的受限项目 API 密钥。
- 密钥通过 Obsidian SecretStorage 保存，禁止写入 Vault、插件 `data.json`、日志或 Git。
- 网络请求使用 Obsidian 官方网络 API。
- 调用前展示会发送的文件范围；敏感客户资料默认排除。
- 第一版记录请求时间、动作类型、模型和错误码，但不记录密钥和完整敏感正文。
- 如果未来对外分发或多人使用，必须改为服务端或本地可信代理，不能沿用客户端直连密钥作为商业架构。

### 10.4 失败与恢复

- AI 失败不推进任务阶段。
- AI 输出先写临时预览，用户接受后再写正式文件。
- 覆盖文件前保存可回滚版本或明确差异。
- 超时、限流、余额不足和无权限需要给出不同错误提示。
- 重试必须幂等，不能重复创建同名资产。
- 用户在 AI 运行期间关闭 Obsidian 时，不创建正式资产；若 API 已返回但尚未接受，只恢复预览，不推进状态。

### 10.5 平台跳过规则

- `skipped` 只能由用户在选题确认后、进入该平台稿件的最终人工核验前选择，并必须填写原因。
- 若在 `drafting` 前跳过某平台，该平台不要求生成稿件，关卡只检查未跳过的平台。
- 若稿件已生成后再跳过，稿件保留并标记停止原因，不删除、不伪装成已发布。
- 至少一个平台必须继续到 `published`，任务才可进入 `retrospective`；两个平台都跳过时任务只能进入 `archived`，并记录停止原因。

## 十一、MVP 范围

### 11.1 P0 必须交付

1. 今日工作台。
2. 内容任务卡及资产聚合。
3. 内容流水线和状态筛选。
4. Brief、爆款设计、双平台稿的创建与打开。
5. 人工关卡清单与状态拦截。
6. 七个明确 AI 动作全部进入 P0；AI 检查是辅助意见，人工核验清单仍是硬门槛。
7. Inbox 新素材列表与快速选题入口。
8. 视频号与公众号分别进行审核、跳过确认和发布事实登记。
9. 表现数据录入、结构化复盘和归档 + 轻量提取门槛，跑通完整闭环。
10. AI 失败不破坏文件、缓存可重建、并发冲突检测和逐崩溃点确定性恢复。

### 11.2 P1 下一阶段

- 历史选题去重。
- 任务阻塞时间和本周节拍统计。
- Hook、主题和平台表现的聚合分析。
- 更细的复盘图表与趋势比较。

### 11.3 后续候选

- 竞品拆解模式库。
- Hook 和主题表现分析。
- 本地后台服务。
- 平台接口接入。
- 移动端轻量审核。

### 11.4 MVP 纵向实施切片

P0 不允许一次性“大爆炸”交付，按以下顺序逐片验收；前一片未通过，不进入后一片：

1. **只读发现切片**：扫描 3 条试点内容，建立任务卡视图、关联资产和不一致报告；不写业务文件。
2. **单任务状态切片**：完成一个任务的阶段推进、人工审核哈希、双平台独立状态和缓存重建；不接 AI。
3. **单资产 AI 切片**：从选定素材生成一个 Brief 预览，完成接受/拒绝、并发冲突和确定性恢复。
4. **双平台创作切片**：爆款设计、视频号稿、公众号稿、修改返工和独立审核全部跑通。
5. **闭环切片**：双平台发布/跳过、数据录入、复盘、素材归档与轻量提取跑通。
6. **稳定性切片**：对所有崩溃点、外部同步、重复 ID、磁盘错误和密钥异常做完整回归。

每个切片都必须提供：可运行演示、自动化测试、对试点 Vault 的前后差异、失败恢复证据和用户验收记录。

## 十二、模块架构

```text
plugin-shell/
  views/              今日工作台、流水线、Inbox、任务详情
  application/        用例编排：创建任务、推进关卡、生成资产
  domain/             ContentTask、状态机、关卡规则
  infrastructure/
    vault/            Markdown/YAML 读写、链接解析、索引重建
    ai/               AI Provider 接口与第一版实现
    cache/            可重建索引和 UI 偏好
  prompts/            动作级提示词装配，不保存密钥
```

原则：

- 领域层不依赖 Obsidian UI。
- AI Provider 不直接修改文件。
- 文件写入必须经过应用层和关卡规则。
- 缓存丢失不能导致业务数据丢失。

## 十三、异常与边界场景

必须在第一版测试：

1. 关联文件被用户手动重命名或移动。
2. 两份文件出现重复 `id`。
3. Brief 存在但爆款设计缺失。
4. 只生成了一份平台稿。
5. AI 请求中途断网或返回空内容。
6. 用户在 AI 运行时关闭 Obsidian。
7. 用户拒绝 AI 修改，原文保持不变。
8. 文件被外部同步程序同时修改。
9. API 密钥缺失、无效、余额不足或限流。
10. Inbox 没有新素材时触发快速选题。
11. 插件缓存删除后重新扫描 Vault。
12. 非 Markdown 原始资料只能关联和预览，不被误当作已清洗知识笔记。
13. 视频号已发布但公众号尚未发布，任务必须停留在 `publishing`。
14. 已审核稿件被人工改写后，旧审核记录必须自动失效并阻止发布登记。
15. `pending_operation` 存在时重启插件，能够检测并恢复，不重复写入。
16. 操作日志已 `prepared` 但尚未写入任何目标时崩溃，可安全继续或回滚。
17. 正式文件已写为新哈希、但日志尚未更新为 `applied` 时崩溃，重启后不得重复写入或创建。
18. 多文件只写入一部分时崩溃，重启后能按逐项状态继续，或在全部快照有效时回滚。
19. 所有资产已应用、但任务最终提交失败时，重启后能重试提交；任务 revision 冲突时停止并人工修复。
20. 新文件在操作期间被外部程序抢先创建时，插件判定冲突且不覆盖。
21. 任务文件在操作期间被外部修改时，最终提交必须失败且不清除恢复日志。
22. 暂存目录空间不足、写入失败或哈希校验失败时，正式文件保持完全不变。
23. 某个平台在生成前被用户 `skipped`，流程只要求另一平台；两个平台都跳过时不得进入复盘。

## 十四、验收标准

### 14.1 产品验收

- 用户打开插件后 10 秒内能指出首要任务和原因。
- 完成一个既有选题从任务卡创建到双平台独立发布和复盘，全程不进入代码或手工修改 YAML。
- 用户可从任务卡一键打开所有关联资产。
- 未满足关卡时，插件明确列出缺失项并阻止错误推进。
- 快速选题在无新素材时正确提示，不自动借用旧素材。

### 14.2 数据安全验收

- AI 调用失败不会覆盖正式稿件或推进状态。
- 插件卸载后所有正式内容仍可用 Obsidian 正常打开。
- 删除插件缓存后可以从 Vault 重建任务列表。
- API 密钥不出现在 Vault、Git、普通日志和导出文件中。
- 所有文件变更有预览或可回滚记录。
- 外部同步冲突时插件停止写入并展示差异，不产生静默覆盖。
- 人工审核记录与稿件哈希绑定，稿件变更后旧审核不能继续放行。
- 对 prepare、逐项 apply、日志落盘、任务最终提交的每一个崩溃点都有自动化恢复测试，恢复结果不会重复创建或静默覆盖。

### 14.3 MVP 成功指标

第一轮用 3 条真实内容验证可走通性和数据安全，不用 3 条样本宣称效率提升。记录：

- 从选定素材到双平台初稿的用时。
- 用户为判断“下一步做什么”花费的时间。
- 人工审核和返工轮数。
- 文件关联或状态错误数量。
- AI 失败后的恢复成功率。

达到以下结果才进入第二阶段：

- 3 条内容均跑到双平台 `ready`；每个平台状态独立正确。
- 至少 1 条内容在视频号和公众号真实发布并完成复盘；其余平台如不发布，必须由用户明确 `skipped` 并填写原因。
- 0 次不可恢复的数据丢失或错误覆盖。
- 用户不需要进入 Codex 或手工编辑 YAML 才能完成主流程。

第二阶段的效率门槛需要再连续测量至少 5 条内容。只统计流程协调时间（找文件、判断下一步、更新状态、关联资产），不把模型生成等待时间和内容质量审核时间混在一起。建议通过线为中位协调时间相对实测基线下降至少 30%；未达到时先修正工作流，不扩功能。

## 十五、分发与开发安全

- 插件源码应放入现有 `obsidian-kb` 项目的独立包或应用目录，具体位置在工程评审阶段确定。
- 开发必须使用单独的测试 Vault。Obsidian 官方明确不建议在主 Vault 中直接开发插件。
- 第一阶段通过手动安装或测试发布验证，不提交社区插件市场。
- 每次试点前保留 Vault 快照；迁移脚本必须先在副本运行。
- 后续若进入公开分发，再设计 GitHub Release、版本升级和兼容矩阵。

## 十八、我观察到的设计取向

- 你先追问“插件能不能做到跟软件一样”，说明你不愿意在载体没定时讨论局部页面；这个顺序是对的。
- 你明确要求“直接在插件里面操作”，因此双工具切换不应被包装成软件方案。
- 你选择今日任务优先，说明这个产品的价值是降低决策成本，不是展示更多信息。
- 你允许明确推荐自动采用，但人工发布与验收仍保留，这要求系统区分“可自动决策”和“必须人工确认”。
