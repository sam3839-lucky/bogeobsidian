# AI Agent 协同系统：深度评审与落地方案

日期：2026-08-12

## 最终裁决

原方案方向正确，但工程定义不完整。它说明了角色和模型分层，却没有解决四个更关键的问题：什么时候不该调用 Agent、什么时候升级才值得、怎样证明任务完成、怎样持续校准成本。

直接照原方案搭建，容易得到一个看起来像团队、实际放大 token、延迟与错误传播的系统。目标应该改成：

> 以最小可靠路径完成任务。默认单 Agent；只有风险、上下文隔离、独立审查或真实并行收益明确时，才增加 Agent 或升级能力。

第一阶段使用 Codex 原生规则、技能和自定义 Agent，不立即开发独立调度平台。

## 一、应保留的部分

1. 角色和模型解耦。同一个角色可按风险选择不同能力。
2. 路由、状态、重试、事件和验证优先使用普通代码或工具。
3. 风险闸门高于复杂度评分；任务短不等于风险低。
4. 测试、类型检查、静态分析和实际行为优先于模型审查。
5. Agent 传结构化契约，不传完整聊天。
6. 任务管理应由事件驱动，而不是让 PM Agent 周期性询问进度。

## 二、必须修正的七个假设

### 1. 低成本模型写代码，高成本模型做规划

代码风险由失败后果、影响范围、可逆性和验证能力决定，不由“是不是代码”决定。权限、财务、生产迁移可能只有几十行，却需要最高等级规划和审查；覆盖充分的局部重构反而可以由标准执行层完成。

正确规则：先过风险闸门，再考虑复杂度和成本。

### 2. Cheap First，失败再升级

它只适用于低后果、可逆、便于验证的任务。对数据删除、权限、支付与生产操作，廉价失败的损失可能远大于模型差价。

正确规则：选择最小可靠路径，不是最低首次调用价。

### 3. 一个数字评分就能自动路由

原方案中 30%、15% 等权重没有实证依据，会制造虚假精确。在没有代表性任务集与结果数据前，权重只是主观判断的数学包装。

V1 使用硬规则和决策树。积累至少 30 个真实任务后，再用数据调整阈值。

### 4. Reviewer Agent 等于质量保障

如果 Reviewer 使用相似模型、相同上下文和同一错误假设，它可能只是把错误换一种措辞。质量顺序应为：

1. 确定性验证。
2. 独立证据。
3. 语义与风险审查。
4. 必要时人工验收。

Reviewer 只覆盖机器无法验证的部分，而且应看到原始证据和变更，不是开发者自我总结。

### 5. PM、Knowledge、Summary 都应常驻

状态迁移、时间戳、任务队列、测试结果和文件索引应由确定性系统维护。只有需要向人解释、综合判断或提炼长期知识时才调用模型。

V1 不设置常驻 PM、Knowledge 或 Summary Agent。

### 6. 多 Agent 天然提高效率

官方文档说明，每个子 Agent 都会进行自己的模型和工具工作，因此多 Agent 比相同任务的单 Agent 消耗更多 token。它的真实价值是缩短可并行任务的等待、隔离噪声上下文、提供独立审查。[OpenAI Subagents 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)

默认子 Agent 数量应为零。

### 7. 可以预先承诺节省 60%

原对话中的 60% 没有输入输出用量、缓存命中、失败率、返工和任务样本支撑，不能用于技术决策。必须先建立基线，再测量。

## 四、四条执行路径

| 路径 | 进入条件 | Agent 使用 | 验证 |
|---|---|---|---|
| A 直接执行 | 清晰、局部、可逆、易验证 | 当前 Agent；0 子 Agent | 确定性检查 |
| B 受控执行 | 一般研究、诊断、开发 | 当前 Agent；必要时一个低成本 Explorer | 检查与行为验证 |
| C 专家规划 | 模糊、跨模块、架构或长期影响 | Sol Planner + 当前 Agent；按需 Terra Reviewer | 契约验收与检查 |
| D 关键任务 | 生产、删除、迁移、权限、支付、安全、隐私 | Sol Planner + 当前 Agent + Sol Critical Reviewer | 备份、回滚、检查、审批 |

当前推荐模型配置：

| 角色 | 配置 | 适用原因 |
|---|---|---|
| 日常主执行 | GPT-5.6 Terra，low 或 medium | 成本与可靠性平衡 |
| 窄范围探索 | GPT-5.6 Luna，low，只读 | 高容量、低风险、输出可压缩 |
| 复杂规划 | GPT-5.6 Sol，high，只读 | 模糊、多步、长期决策 |
| 一般审查 | GPT-5.6 Terra，high，只读 | 边界推理，但不总需旗舰 |
| 关键审查 | GPT-5.6 Sol，high，只读 | 高后果失败模式 |

OpenAI 官方资料将 Sol 定位为复杂专业工作，Terra 定位为智能与成本平衡，Luna 定位为成本敏感、高吞吐工作。reasoning 越高通常增加 token 与延迟，必须用真实任务验证收益。[GPT-5.6 指南](https://developers.openai.com/api/docs/guides/latest-model)

## 五、子 Agent 的准入条件

以下至少一项成立时才使用：

1. 两项工作真正独立，能并行缩短等待。
2. 探索、日志或大文件会显著污染主上下文。
3. 需要与实现者独立的风险审查。
4. 子任务有窄输入、明确输出与停止条件。

以下情况禁止使用：

1. 单 Agent 可在有界上下文内完成。
2. 多个 Agent 只会读取相同资料并重复表达。
3. 多个 Agent 同时修改同一工作区。
4. 只是为了模拟团队感。
5. 没有合并标准与验收证据。

默认并发上限为两个，默认只有一个写入者。

## 六、失败、重试和升级

同一路径最多重试一次。重试前必须找出失败原因，并改变输入、工具、假设或验证方式。第二次仍失败，或者风险扩大、证据冲突、任务范围改变时，升级到下一路径。

失败有时来自环境、权限、依赖或错误验收条件；无脑换大模型不能解决这些问题。

## 七、上下文与状态

Agent 上下文只包含：

- 当前任务与成功标准。
- 相关项目约束和关键决策。
- 相关文件或资料。
- 已验证证据。
- 当前失败与待解问题。

不要自动携带完整历史聊天、整个仓库或其他 Agent 的过程记录。

一次性任务不创建管理文件。跨会话任务才使用：

    .ai-team/
      TASK_STATE.md
      DECISIONS.md
      METRICS.csv

Planner 输出规划契约，使执行者无需重读规划对话即可工作。契约包括目标、非目标、约束、假设、任务、验收、风险、回滚和审批点。

## 八、度量：没有数据就不谈节省

前 30 个真实任务记录：

- 路径 A、B、C 或 D。
- 子 Agent 数量。
- 重试次数。
- 首次验证是否通过。
- 用户纠错次数。
- 是否产生回归。
- 完成时间与验证类型。
- 若可获取：输入、缓存、输出 token 和实际成本。

核心判断：

1. 任务成功率和首次通过率不能下降。
2. 比较每个成功任务的总成本，而非单次调用价格。
3. 检查升级率是否过高或过低。
4. 检查子 Agent 是否带来独立证据或时间收益。
5. 检查用户纠错和回归是否集中在某一路径。

Codex 客户端未提供用量时，token 和成本字段留空，使用调用数、重试、子 Agent、首次通过与完成时间作为代理指标。需要精确逐调用账本时，再建设 Responses API 编排层。

## 九、Codex 原生落地方式

采用三层：

1. 全局 AGENTS.md：只放最稳定、最短的治理原则，所有项目继承。
2. 个人 skill：保存完整路由、重试、上下文和验证流程，按需加载。
3. 自定义 Agent：Explorer、Planner、普通 Reviewer 与关键 Reviewer 使用不同模型和只读边界。

这里的模型路由是委派式路由：运行中的主 Agent 不会原地热切换模型，而是把窄任务交给预配置的专用 Agent，再综合结果。[Codex 自定义 Agent 文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)

## 十、让后续所有工作采用这套方案

### 1. 安装个人级规则

运行交付包的 install.ps1。它会：

1. 备份现有个人 AGENTS.md。
2. 保留原来的“严苛导师”规则，追加成本感知协议。
3. 安装个人 skill。
4. 安装四个专用 Agent。

安装脚本不修改默认模型，也不删除原配置。

### 2. 重启 Codex 或新建任务

AGENTS.md 在任务启动时读取。安装后开启新任务，让规则链重新加载。官方说明，全局 AGENTS.md 会被所有项目继承，更靠近工作目录的项目规则可以覆盖它。[AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

### 3. 每个真实项目补充项目规则

全局规则解决“怎么工作”，不能猜出项目测试命令、架构边界和发布要求。每个项目根目录仍应放一份简短 AGENTS.md，写明：

- 允许修改的范围。
- 测试、构建与检查命令。
- 关键架构约束。
- 高风险目录与人工审批点。
- 项目的完成定义。

不要复制完整全局协议，只保存项目差异。

### 4. 后续正常说目标

安装后无需每次复制长提示词。非简单任务会匹配个人 skill。关键任务或需要查看路由依据时，可以明确说：

    使用 cost-aware-execution 完成这个任务。
    先明确风险和成功标准，选择最小可靠路径；
    必要时升级，但不要为了分工而分工。

### 5. 30 个任务后校准

- A、B 路径频繁返工的任务应升级。
- C、D 路径从未发现附加风险的任务可以尝试降级。
- 只重复自动检查的 Reviewer 应取消。
- 没有降低主上下文噪声的 Explorer 应取消。

## 十一、什么时候开发独立调度平台

只有出现以下需求时才进入 Responses API 编排版：

- 跨用户或跨项目统一队列。
- 精确逐调用 token、成本、缓存和 SLA。
- 后台任务、Webhook、批处理或自动恢复。
- 根据历史评测自动学习路由阈值。
- Codex 原生任务和技能无法满足吞吐量。

在此之前，自建 FastAPI、Redis、PostgreSQL、向量数据库和 LangGraph 会增加运维面，未必节省 token。

## 十二、验收标准

1. 质量不低于当前基线。
2. 关键任务不绕过风险闸门。
3. 普通任务绝大多数不创建子 Agent。
4. 每次升级都有明确原因。
5. 每次完成都有可复核证据。
6. 30 个真实任务后，成功任务的总成本或完成时间有可测改善。

如果第 6 项不成立，应简化系统，而不是继续增加 Agent。
